# Why Are We Here?

## If AI Can Write Code, Why Am I Learning It?

At first, the answer seemed easy: programming is useful, so it is worth learning. But that felt strange when I considered how I actually work.

As an interaction design student, I can already describe an idea to AI and get working code back in seconds. If I want a button, an animation, or a simple interaction, AI can often give me a starting point before I fully understand how the code works.

This made me question what I am actually trying to learn. I am not learning programming to become faster at writing code than AI. I want to understand what I am actually asking the machine to do, and I want to know when its answer is not really my answer.

## I Thought “Less Crowded” Was Already a Design Decision

I realised this while working on a recent interaction design project called **CrowdEscape**.

CrowdEscape is a navigation concept that focuses on how a route feels instead of only how fast it is. I wanted users to have choices such as **Quietest**, **Less Crowded**, and **More Outdoor**, rather than always being sent along the fastest route.

At first, “Less Crowded” felt quite specific to me. I could tell AI:

> Build a navigation feature that avoids crowded areas.

But once I thought about how this would actually work, a simple question appeared: what does “crowded” mean?

Imagine one route takes ten minutes but passes through a packed station. Another takes eighteen minutes but is mostly outdoors. Which one should the system choose?

I realised that I had not really designed “Less Crowded” yet. **I had designed the idea of it.**

A computer eventually needs actual rules. What information counts as crowding? How much extra walking time is acceptable? When should it recalculate the route?

**Programming shows me what I have not decided yet.**

## Working Is Not the Same as Being Right

AI-generated code can work and still make design decisions I did not intend.

Imagine AI builds the Less Crowded feature. The map appears, the button works, and a new route is generated. It would be easy to think: done.

But why did it choose that route?

Maybe it is using real crowd information. Maybe it is using a shortcut I did not ask for. Maybe it works in the example I tested but fails when some data is missing.

So I cannot judge the result only by asking, “Does it run?” I also need to ask what it assumes, what controls it, and what happens when something unexpected occurs.

Without understanding the code, I risk accepting a result simply because it looks convincing.

## Do I Have to Write Every Line for It to Be Mine?

This leads to another question: if AI writes some of the code and I am mainly reading, questioning and changing it, is the result still my work?

I do not think I need to type every line for a project to be mine. But asking AI for ten versions and choosing my favourite is not enough either.

For me, there is a difference between choosing a result and understanding why that result happened.

If CrowdEscape keeps giving people very long routes because of the way “crowded” is calculated, I want to be able to find that decision and change it. I do not want my only option to be:

Try again.

I may not have written every line, but if I can understand a rule, question it, change it, and take responsibility for the result, I am still making decisions inside the work.
## Code Is Part of the Material

Dylan Beattie’s talk *[The Art of Code](https://www.youtube.com/watch?v=6avJHaC3C2U)* (NDC Conferences, 2020) made me think about programming as something expressive, not only technical.

This connects to Ihde’s (1990) *[Technology and the Lifeworld](https://iupress.org/9780253114167/technology-and-the-lifeworld/)*: technology is not completely neutral. Our tools can affect how we experience things and what we imagine we can make.

A painter needs to understand paint. A photographer needs to understand light. For an interaction designer, I think code, data and rules are also part of the material.

I do not want to become a software engineer. But if I know nothing about what is behind an interaction, I might design what the screen looks like without really understanding what the system can do.

## The Artist Does Not Have to Draw Every Line

In 1965, Frieder Nake created *[Hommage à Paul Klee Nr. 2](https://zkm.de/en/artworks/hommage-a-paul-klee-nr-2)* using a program he wrote and a plotter. He created rules while leaving space for unexpected results (Drago Jekal, n.d.).

The computer made the drawing, but its rules were still part of Nake’s creative decisions.

Generative AI differs from a plotter in 1965, but Nake’s work offers another perspective on authorship. Maybe making a work does not always mean controlling every final detail. Sometimes it means understanding and shaping the system that produces those details.

## What Am I Actually Learning?

Some things I learn will probably become outdated. Libraries and software will change, and future designers may rarely write basic code themselves. I am okay with that.

What I want to learn is something underneath those tools: how to turn an unclear idea into rules, understand why a system behaves in a certain way, and notice when something that looks correct is not actually doing what I wanted.

AI may make the question “How do I write this?” much easier.

But that makes another question more important:

**What exactly do I want this to do?**

## Why Am I Here?

I do not want to accept the first answer just because AI made it quickly and it seems to work.

I want to notice when my own idea is still unclear, understand what decisions a system has made for me, and know enough to change those decisions when they are wrong.

AI could help me write the code for CrowdEscape.

But I still have to decide what “crowded” means.

**AI can generate an answer. I need to know whether that answer is worth keeping.**

That is why I am here.
